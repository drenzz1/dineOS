# DineOS — Database Schema

> Companion to [`ERD.md`](./ERD.md). The ERD shows relationships; this file
> documents column-level details, the **3NF normalization review**, and the
> migration history/strategy.

- **DBMS**: PostgreSQL (Npgsql EF Core provider)
- **DbContext**: [`backend/src/DineOS.Infrastructure/Persistence/AppDbContext.cs`](../../backend/src/DineOS.Infrastructure/Persistence/AppDbContext.cs)
- **Model snapshot**: [`AppDbContextModelSnapshot.cs`](../../backend/src/DineOS.Infrastructure/Persistence/Migrations/AppDbContextModelSnapshot.cs)
- **Migration workflow & strategy**: [`docs/database-migrations.md`](../database-migrations.md)

## Base classes

```
BaseEntity
└── Id : bigint (identity, PK)

BaseAuditingEntity : BaseEntity
├── CreatedAt : timestamp with time zone
├── CreatedBy : text NULL
├── UpdatedAt : timestamp with time zone NULL
├── UpdatedBy : text NULL
├── DeletedAt : timestamp with time zone NULL   -- soft delete marker
└── DeletedBy : text NULL

TenantAuditingEntity : BaseAuditingEntity
└── TenantId : bigint
```

`DeletedAt` is the soft-delete marker; rows are excluded from queries via an
EF Core global query filter. The filter on `TenantAuditingEntity` additionally
restricts rows to the current tenant unless tenant context is unset (SuperAdmin).
Every primary key uses `GENERATED BY DEFAULT AS IDENTITY` (Npgsql identity).

## Normalization (3NF)

The schema satisfies **third normal form**: every table has a single-column
identity PK, all non-key attributes depend on the whole key, and there are no
transitive dependencies between non-key attributes.

### Table-by-table

| Table | 1NF | 2NF | 3NF | Notes |
|-------|:---:|:---:|:---:|-------|
| Tenants | ✅ | ✅ | ✅ | Stripe/billing fields all depend directly on the tenant key. Derived aggregates removed (below). |
| StaffMembers, Orders, OrderItems, MenuCategories, MenuItems, ShiftNotes, RestaurantTables, Shifts | ✅ | ✅ | ✅ | Atomic columns; every attribute depends on `Id`. |
| Payments | ✅ | ✅ | ✅ | |
| TenantInvoices, EmailVerificationCodes, DeadLetterEmails, ProcessedMessages | ✅ | ✅ | ✅ | Single-key tables; no inter-attribute dependencies. |

### Normalization fixes applied (M5.3)

1. **`MenuItem.Category` (text) → `MenuItem.CategoryId` (FK → `MenuCategories`).**
   The old text column duplicated the category name across every item and was
   completely disconnected from the `MenuCategories` table — two competing
   sources of truth for one fact, and no referential integrity. The category
   name now lives **once** in `MenuCategories.Name`; items reference it by FK.
   The HTTP API is unchanged (it still speaks category *names*) —
   `MenuService.ResolveCategoryAsync` maps a name to the FK (get-or-create per
   tenant). Existing rows were migrated, not dropped.

2. **Removed `Tenant.TotalOrders`, `Tenant.StaffCount`, `Tenant.Revenue`.**
   These were stored aggregates derived from `Orders`, `StaffMembers` and
   `Payments` — redundant, derivable data that violates normalization (and they
   were never maintained, so they always read 0). They are now computed on
   demand in `AdminRestaurantService` (`COUNT`/`SUM` over the source tables).

### Intentional denormalization (documented)

- **`OrderItems.Name` and `OrderItems.UnitPrice`** duplicate the menu item's name
  and price *at order time*. This is a deliberate **historical snapshot**: an
  order's line items must not change if the menu is later re-priced or renamed.
  This is point-in-time data, not redundant derivable data, so it does not
  violate 3NF in the practical sense.

## Verifying the running schema matches

```bash
# Dump only the schema (no data) and compare against the model snapshot
docker compose exec postgres pg_dump --schema-only --no-owner --no-privileges \
  -U dineos -d dineos > /tmp/dineos-schema.sql
```

The dumped tables, columns and FKs should match
[`AppDbContextModelSnapshot.cs`](../../backend/src/DineOS.Infrastructure/Persistence/Migrations/AppDbContextModelSnapshot.cs)
exactly. If they diverge, either a migration was applied manually or the snapshot
is stale — regenerate by adding a new migration.
